Две сцены.

**Сцена первая.** Разработчик правит один файл в `core/types/`. Открывает PR. CI 12 минут билдит весь монорепо, потом ещё 4 минуты гоняет интеграционные тесты для приложений, которые этот пакет даже не импортируют. Через 16 минут зелёная галка. Все привыкли — «у нас же 80 пакетов, иначе никак».

**Сцена вторая.** Тот же разработчик ставит на PR лейбл `preview`. CI собирает три docker-образа, пушит их в registry, поднимает на VPS web/api/docs контейнеры, рисует три субдомена. Reviewer открывает URL — там тот же сайт что в main, потому что изменения были в `core/`, к которому фронт не обращается. RAM съедена, преview-стек висит до закрытия PR.

Эти две сцены про одну и ту же дыру в платформе, и обе подсвечивают что мы делали неправильно.

## Поверхностное прочтение

Большинство монорепо-инструментов умеют **affected detection**: сравнить diff с предыдущей точкой, найти изменённые пакеты, добавить downstream'ы через граф зависимостей, пересобрать только это. Turbo, Nx, kb-devkit — все так умеют.

Подача обычно такая: «affected ускоряет сборку». И это правда, но это — самый дешёвый из эффектов. Build-skip экономит секунды. На таком уровне affected — это про **runtime оптимизации**.

Это поверхностное прочтение, и оно загоняет тебя в ловушку: ты применяешь affected только к шагам, которые легко измерить в секундах. Build, test, lint. И останавливаешься.

## Глубокое прочтение

Affected — это **не оптимизация одного шага**. Это утверждение про то, какая часть мира относится к текущему изменению. Это **входной сигнал для решения**: делать ли работу вообще.

Если переформулировать так — становится видно, что один и тот же сигнал применим на каждом уровне стека, и каждый уровень открывает новое решение.

### Уровень 1: исходники (build-affected)

Решение: **какие пакеты пересобирать**. Ответ движет компилятор. Экономия — секунды CPU.

```bash
kb-devkit run build --affected
```

### Уровень 2: артефакты (deploy-affected)

Решение: **какие docker-образы собирать и пушить в registry**. Ответ движет CI и сетевой трафик. Экономия — десятки секунд + место в registry + не дёргается production rollout, когда нет причин его дёргать.

```yaml
# .kb/deploy.yaml
targets:
  kb-gateway:
    watch: [plugins/gateway/**, core/**, shared/**]
    image: kb-gateway
```

kb-deploy сравнивает `watch:` глобы с git diff. Если ни один файл не попал — таргет пропущен. Никакого build, никакого push, никакого ssh.

### Уровень 3: окружения (environment-affected)

Решение: **поднимать ли preview-стек на VPS вообще**. Ответ движет уже не CPU и сеть, а целый docker compose: контейнеры, RAM, порты, nginx-роуты, субдомены. Экономия — минуты времени, ~1 ГБ RAM, чистота PR thread'а (нет лишнего комментария «вот превью», который никто не откроет).

Это самый дорогой уровень — и именно его принято делать «всегда поднимать на PR». Vercel поднимает превью на любой commit. Render — тоже. Все CI-инфра-вендоры рекламируют «preview на каждый PR» как фичу.

Но это **дорогая по умолчанию** стратегия, выгодная вендору (вы покупаете больше runtime), а не команде. PR, который трогает только серверную бизнес-логику или внутренние плагины — не имеет user-facing изменений. Поднимать ему стек из трёх контейнеров — это шум, не полезное действие.

В нашем CI это сейчас выглядит так:

```bash
CHANGED=$(git diff --name-only origin/main...HEAD)
AFFECTED=()
[[ "$CHANGED" =~ ^sites/web/apps/web/  ]] && AFFECTED+=(web)
[[ "$CHANGED" =~ ^sites/web/apps/docs/ ]] && AFFECTED+=(docs)
[[ "$CHANGED" =~ ^plugins/gateway/|^core/|^shared/ ]] && AFFECTED+=(gateway)
[[ ${#AFFECTED[@]} -eq 0 ]] && { echo "no UI affected — skipping preview"; exit 0; }
```

Восемь строк. Решение: запустить ли пайплайн из ~10 минут работы. Если в PR нет ничего видимого глазом — пайплайн не запускается. Никто не теряет ничего.

## Композиция уровней

Самое интересное случается, когда уровни складываются.

Возьмём PR с одним коммитом в `sites/web/apps/web/components/Header.tsx`.

- **Уровень 1** говорит: пересобрать только `kb-labs-web` и его обратные зависимости.
- **Уровень 2** говорит: запушить только `ghcr.io/.../kb-site-web` (gateway и docs не трогаем).
- **Уровень 3** говорит: поднять preview только с web-контейнером. Никаких gateway и docs.

Каждый уровень **отвечает на тот же вопрос** (что изменилось?), но решает свою задачу. Один сигнал — три экономии. И каждая экономия на порядок больше предыдущей: секунды → минуты → минуты+RAM+UX.

## Где этого нет

Хороший индикатор отсутствующей абстракции — когда у тебя есть «делать или не делать» решение, для которого нет однозначного ответа. Обычно ты затыкаешь его флагом: `if: env.BRANCH == 'main'`, `--all`, manual approval. Эти затычки накапливаются, и платформа теряет способность принимать решения сама.

Если поймал себя на такой затычке — это сигнал, что не хватает affected на этом уровне. Спроси: **что система уже знает про моё изменение?** Если ответ есть — это вход. Если ответа нет — это та абстракция, которую стоит добавить.

## Имплементационная заметка

Чтобы это работало, `watch:` глобы должны быть выражены **одинаково на всех уровнях**. У нас это путь-глобы: `plugins/gateway/**`, `sites/web/apps/web/**`. Один и тот же синтаксис в kb-devkit, в kb-deploy, в preview-pipeline.

Это не случайность. Когда один сигнал используется на трёх уровнях, он обязан иметь общее представление — иначе расходятся, и платформа начинает делать на двух уровнях противоречивые выводы. Появляется баг-класс «build пропустил X, но deploy собрал X — почему?». Лечится только сведением представления к одному.

## Принцип

> Affected — это не оптимизация сборки. Это **входной сигнал для каждого решения «делать или не делать»** на любом слое платформы.

Если ты строишь платформу — каждый раз, когда у тебя возникает новое «делать или не делать», задай вопрос: «что говорит affected?». Если ответ есть — это уже вход. Если ответа нет — это абстракция, которой не хватает.

У нас этот вопрос привёл к трём независимым реализациям — на уровне сборки, артефактов и окружений. Все три родились в разное время, для разных задач. Когда я недавно собирал их вместе для preview environments — стало видно, что это **один и тот же приём, применённый трижды**. Каждый раз — другой класс экономии.

Это и есть форма зрелой платформы: одно знание, несколько применений. Без размножения логики.
