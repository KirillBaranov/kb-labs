Open-source продукт. README говорит «деплой за 10 минут». Пользователь клонирует, ставит, и через минуту получает 502 — потому что мейнтейнеры держат перед сервисом nginx с конкретным `proxy_pass` на порт, и забыли это упомянуть. Или ещё хуже: репо реально содержит prod-конфиг с захардкоженным IP, и однажды в коммит улетел API-ключ.

Это два разных провала, но симптом один: **попытка сделать одним репо две разные работы**.

## Поверхностное прочтение

«Нам нужно разделить — где пример, а где реальный конфиг». Поэтому появляются папки `examples/`, `docs/deployment-example/`. Документация. Notes в README.

Так делают почти все. И это **не работает в долгую**: пример живёт отдельно от реальности, разъезжается с ней через месяц. Никто не идёт обновлять `examples/nginx.conf`, когда меняет настоящий `nginx.conf` на проде. Через год пример сломан, и новые пользователи получают 502.

## Глубокое прочтение

Это **два разных артефакта** с разными свойствами.

**Reference deployment** — это часть продукта. Generic. С плейсхолдерами вместо доменов и портов. Обновляется когда меняется модель сервиса (новый параметр в config, новый порт по умолчанию). Версионируется вместе с продуктом. Контрибьюторы видят, ревьюят, тестируют. Это **публичный артефакт**.

**Production deployment** — это операторская сущность твоей команды. Конкретные домены, конкретные сертификаты, IP-адреса, привычки. Обновляется когда тебе удобно. Содержит секреты в открытом виде или зашифрованные. Это **приватный артефакт**.

У них **разные жизненные циклы**, разные read/write правила, разные ауди­тории. Сжать их в один репо — это как поместить production-БД и SQL-tutorial в одну схему. Поломаешь либо обучение, либо прод.

## Что не работает

Несколько подходов выглядят разумными, и я бы хотел сэкономить тебе час раздумий:

**Один публичный репо + `.gitignore` на приватные файлы.** Одна опечатка в gitignore — и секрет в публичной git history навсегда. `git clean -fdx` снесёт всю инфру. `find` и `grep` будут лазить в неё. Психологически — это мина под собой.

**Submodule на приватный репо.** Палит сам факт существования через `.gitmodules`. Контрибьюторы не клонируются (не дадут им SSH к приватному). И submodule — это боль обслуживания: pinning, рассинхрон, «забыли обновить».

**«Просто документация».** Расходится с реальностью через 2-3 деплоя. Никто не пишет PR в docs, когда фиксит прод в три часа ночи.

## Что работает

**Два независимых репозитория.** Никаких связей в коде.

- **Публичный**: монорепо продукта. Внутри — `templates/nginx/`, `templates/deploy/`, `templates/plugin/`. Шаблоны с `{{ DOMAIN }}`, `${PORT}`, README по применению. Это часть продукта, контрибьюторы видят, CI билдит, изменения проходят ревью.

- **Приватный**: отдельный репо с конкретной инфрой. Содержит реальный nginx-конфиг с реальными доменами, секреты (или ссылки на secret manager), CI/CD для деплоя на ваш VPS. Никаких ссылок на него из публичного — пользователи не должны даже знать, что он существует.

Связь между ними **только через документацию** в приватном репо: «деплоит продукт `github.com/<org>/<product>`, образы из `ghcr.io/<org>/*`, основан на `templates/nginx/`». Публичный про приватный не знает ничего.

## Когда это окупается

Эта схема дороже однорепной на старте — два места куда коммитить, два workflow поддерживать, две README писать. Окупается она в трёх ситуациях:

1. **Открытый исходник.** Любой репо, где код видит мир. Тут отказ от схемы — это просто вопрос времени до утечки.
2. **Первый клиент.** Когда кто-то ставит твой продукт у себя — становится критично иметь чистый шаблон, отделённый от твоих привычек. Иначе клиент копирует твой `kblabs.ru` в свой конфиг и потом разбирается почему упало.
3. **Команда вырастает.** Junior'у нельзя давать SSH к проду, но можно — PR в `templates/nginx/`. Разделение даёт возможность безопасно делегировать.

## Принцип

> Твой production-deployment — это **не reference deployment**. Поделить их по разным репозиториям — это не дублирование, это **признание двух разных артефактов** с разными правилами.

Когда я недавно настраивал nginx + preview-environments для kblabs.ru — у меня был соблазн сделать всё в монорепо в `infra/` папке. Я отказался по этой же причине. Сейчас у нас `templates/nginx/` (публичный шаблон, generic, для клиентов) и `kb-labs-infra` (приватный, мой прод, со всеми deploy-секретами). Через пару месяцев это окупится первой же попыткой клиента самохостить — у него будет что копировать без необходимости расшифровывать мой `kblabs.ru.conf`.

Не пытайся делать одним репо две разные работы.
