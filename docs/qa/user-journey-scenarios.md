# KB Labs E2E: пользовательские сценарии

E2E должен отвечать на вопрос: «Смог ли пользователь установить KB Labs и
получить работающую ценность?». Отдельный HTTP 200, наличие файла или вызов
одной команды сами по себе не являются пользовательским сценарием.

Каждый сценарий начинается с чистого состояния, проходит через реальные
команды пользователя и заканчивается наблюдаемым результатом. Если
предусловие не выполнено, сценарий красный; необязательные части нельзя
молча пропускать.

## Journey 1 — установить платформу и получить первый рабочий проект

**Персона:** разработчик, который впервые ставит KB Labs на чистую машину.

**Старт:** нет `kb-create`, `kb-dev`, локального KB Labs platform directory и
проектной папки.

**Путь:**

1. Выполнить официальный `install.sh`.
2. Убедиться, что launcher установил все запрошенные бинарные артефакты и
   команды доступны в новом shell.
3. Создать проект через `kb-create` с явно выбранными сервисами и плагинами.
4. Проверить, что manifest отражает именно выбор пользователя: нет лишних
   сервисов и отсутствуют пропущенные обязательные артефакты.
5. Запустить сервисы через `kb-dev start`.
6. Дождаться готовности gateway, state, marketplace, REST API, workflow и
   studio, а не только одного health endpoint.
7. Войти как обычный пользователь и получить рабочую CLI-сессию.
8. Выполнить первую ценную операцию: получить список marketplace и запустить
   установленную команду плагина.

**Успех:** чистая машина превращается в работающий проект; выбранные сервисы
доступны, авторизация работает, а пользователь получил результат команды
плагина.

## Journey 2 — создать свой плагин и сделать его marketplace-артефактом

**Персона:** разработчик, расширяющий KB Labs собственной командой.

**Старт:** Journey 1 завершён, проект и platform directory уже работают.

**Путь:**

1. Создать плагин через scaffold в проекте пользователя.
2. Изменить команду плагина так, чтобы она возвращала проверяемый результат,
   например `Hello from my plugin`.
3. Установить зависимости и собрать плагин обычными пользовательскими
   командами.
4. Запустить плагин из проекта и проверить результат.
5. Добавить плагин в локальный marketplace/registry тем способом, которым это
   делает автор плагина.
6. Обновить индекс marketplace и установить плагин как внешний пользователь,
   а не через прямой импорт исходников.
7. Повторно запустить команду уже из установленного marketplace-пакета.
8. Удалить плагин через marketplace CLI.
9. Проверить, что команда исчезла из discovery, а остальные плагины и сервисы
   продолжили работать.

**Успех:** один и тот же плагин проходит путь `scaffold → build → local run →
publish/register → marketplace install → run → remove`; удаление не оставляет
сломанных ссылок и не удаляет соседние компоненты.

## Journey 3 — platform directory отдельно от project directory

**Персона:** разработчик или CI-агент, который хранит platform runtime отдельно
от исходников проекта.

**Старт:** две чистые независимые папки, например `/tmp/kb-platform` и
`/tmp/my-project`.

**Путь:**

1. Установить платформу в `platform directory`.
2. Создать или подключить проект в другой папке.
3. Запустить команды KB Labs из project directory, явно указывая platform
   directory или используя поддерживаемую конфигурацию.
4. Убедиться, что project directory содержит только проектные файлы и `.kb`
   metadata, а platform directory содержит runtime, binaries и packages.
5. Запустить сервисы и плагин из project directory.
6. Перезапустить shell и повторить команду, чтобы исключить зависимость от
   текущего процесса или случайного `cwd`.
7. Обновить platform directory и проверить, что исходники проекта, его env и
   установленный пользовательский плагин сохранены.

**Успех:** разделение папок является рабочим режимом, а не только валидной
комбинацией флагов; команды одинаково работают из project directory после
перезапуска и обновления платформы.

## Journey 4 — установка и выполнение в CI

**Персона:** CI job, которая каждый раз стартует без локального состояния.

**Старт:** чистый runner с Node, pnpm, curl и git; нет пользовательского
`$HOME/.kb`, локальных credentials и ранее установленной платформы.

**Путь:**

1. Выполнить официальный launcher/install flow в non-interactive режиме.
2. Установить только требуемые CI-плагины и сервисы.
3. Проверить exit code, install manifest, lockfile и наличие бинарей.
4. Запустить требуемый service subset или весь необходимый runtime.
5. Получить machine/service credentials из безопасных CI secrets и проверить
   авторизацию реальным CLI-вызовом.
6. Выполнить полезную операцию внутри CI-контура: запустить плагин, workflow
   или проверку проекта и дождаться terminal status.
7. Собрать логи и артефакты, достаточные для диагностики упавшего шага.
8. Завершить job без записи секретов в stdout, проектный git и cache общего
   назначения.

**Успех:** одинаковый clean runner может выполнить полезную KB Labs-операцию
без ручного вмешательства; провал любой обязательной стадии делает job
красной и оставляет диагностические логи.

## Journey 5 — установка стороннего плагина без разрушения проекта

**Персона:** пользователь, у которого уже есть рабочие `commit` и scaffold,
и который добавляет сторонний release-плагин.

**Путь:**

1. Зафиксировать список доступных команд и установленных пакетов.
2. Установить сторонний плагин через marketplace CLI или V2 `kb-create apply`
   с pinned plugin в sealed release-index.
3. Проверить, что новый пакет и его команда появились.
4. Повторить установку/обновление плагина идемпотентно.
5. Удалить только сторонний плагин.
6. Проверить, что исходные `commit`, scaffold, сервисы, credentials и workflow
   остались рабочими.

**Успех:** add/update/remove меняют только целевой плагин; проект не теряет
ранее установленную функциональность.

## Journey 6 — обновить и удалить платформу безопасно

**Персона:** пользователь, который обновляет KB Labs или больше не хочет
использовать локальный runtime.

**Старт:** рабочая platform directory, отдельный project directory,
пользовательский плагин, `.env`, workflow, lockfiles и пользовательские
исходники.

**Путь обновления:**

1. Зафиксировать контрольный снимок пользовательских файлов: исходники,
   `.env`, project config, workflow, plugin source, lockfiles и platform
   metadata.
2. Выполнить поддерживаемую команду обновления платформы.
3. Проверить, что версия runtime и выбранные пакеты обновились.
4. Перезапустить сервисы.
5. Повторить авторизацию, запуск собственного/стороннего плагина и workflow.
6. Сравнить контрольный снимок: пользовательские артефакты не перезаписаны,
   credentials не потеряны, а конфигурация получила только ожидаемые
   миграции.

**Путь удаления:**

1. Запросить удаление платформы без флага подтверждения.
2. Убедиться, что команда отказалась от destructive action и ничего не
   удалила.
3. Повторить удаление с явным `--yes`/подтверждением.
4. Проверить, что удалена только platform directory и связанные runtime
   artifacts.
5. Проверить, что project directory, исходники, workflow, plugin source,
   `.env` и пользовательские lockfiles сохранились.
6. Убедиться, что повторное удаление идемпотентно и даёт понятный результат.

**Успех:** update не уничтожает пользовательские данные; uninstall является
явно подтверждаемым destructive action и не удаляет проект по умолчанию.

## Journey 7 — установить и сменить адаптер

**Персона:** пользователь, который подключает другой storage/LLM/logging
provider или добавляет адаптер для нового capability.

**Старт:** рабочая платформа с адаптером A и работающим плагином, который
использует соответствующую capability.

**Путь:**

1. Установить адаптер B через поддерживаемый пользовательский install flow.
2. Проверить manifest, lockfile и фактическое наличие пакета/артефакта.
3. Переключить конфигурацию с A на B без ручного редактирования generated
   runtime-файлов, если для этого есть CLI/config flow.
4. Перезапустить только необходимые сервисы и проверить startup diagnostics.
5. Выполнить реальную операцию через capability: например LLM completion,
   запись/чтение storage или логирование запроса.
6. Перезапустить shell и сервисы, чтобы проверить сохранность выбора.
7. Вернуться с B на A либо удалить B.
8. Повторить реальную операцию и убедиться, что удаление не ломает platform
   discovery и соседние плагины.

**Успех:** адаптер можно установить, выбрать, реально использовать, заменить
и удалить; система не сообщает об успешном переключении, пока capability не
работает через новый адаптер.

## Journey 8 — добавить, изменить и выполнить workflow

**Персона:** пользователь, который автоматизирует повторяемую операцию.

**Старт:** рабочая платформа с workflow service и проектом, содержащим
минимальный runnable package.

**Путь:**

1. Установить workflow/plugin capability и убедиться, что workflow service
   запущен.
2. Добавить workflow из shipped template или marketplace.
3. Провалидировать workflow пользовательской командой lint/validate.
4. Выполнить workflow с реальным project input.
5. Получить run id и дождаться terminal status.
6. Проверить логи и результат каждого существенного шага.
7. Изменить workflow — например добавить шаг build/lint/test — и повторно
   провалидировать и выполнить его.
8. Установить второй workflow и убедиться, что первый сохранился.
9. Удалить или отключить второй workflow с подтверждением, если действие
   destructive, и повторно выполнить первый.

**Успех:** workflow проходит полный цикл `install/add → lint → run → status →
logs → edit → rerun → remove/disable`; результат подтверждён не только
созданным run record, но и выполненным пользовательским шагом.

## Общие критерии для каждого journey

- сценарий запускается из чистого или явно описанного состояния;
- используются публичные пользовательские команды и реальные сервисы;
- проверяется результат, которым пользуется человек, а не только exit code;
- авторизация проверяется в том же транспортном пути, что и рабочая команда;
- установка проверяет запрошенный состав, а не просто наличие любого пакета;
- нет `skip`, если обязательный сервис, артефакт или credential отсутствует;
- на failure сохраняются команды, версии, manifest, service logs и последний
  ответ API;
- сценарий повторяем и не зависит от случайной текущей рабочей директории.

## Разделение автоматизации

- V2 E2E в `tools/kb-create/v2/e2e` — post-publish journey с apply/status,
  project pointer, plugin scaffold и workflow run.
- доменные Playwright E2E в `e2e/{auth,marketplace,plugins,services,workflows}`
  — детали marketplace, adapters и workflow внутри journeys, но не замена
  полного пользовательского пути. Они запускаются на platform, собранной из
  текущего checkout и установленной из Verdaccio.
- `.github/workflows/publish-npm-on-tag.yml` — обязательный post-publish V2
  smoke, который запускает journey на точном release-index и сохраняет log.
