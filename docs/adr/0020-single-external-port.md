# ADR-0020: Single External Port (Gateway Only)

**Date:** 2026-05-27
**Status:** Accepted
**Deciders:** KB Labs Team
**Last Reviewed:** 2026-05-27
**Tags:** architecture, security, networking, deployment

## Context

KB Labs spins up several daemons on install: gateway (:4000), rest-api (:5050),
marketplace (:5070), marketplace-registry (:5071), workflow (:7778), state (:7777),
studio (:3000). All of them defaulted to binding on `0.0.0.0`, exposing every
internal service to the local network.

This created two problems:

1. **User friction** — developers on shared networks (offices, co-working spaces)
   saw all KB Labs ports appear on the network, interfering with colleagues or
   tripping firewall rules.
2. **Security surface** — internal services (rest-api, workflow, marketplace) have
   no authentication on their own; they rely on gateway to enforce auth. Exposing
   them directly bypasses that layer.

## Decision

Only the **gateway** binds to `0.0.0.0`. All other daemons bind to `127.0.0.1`
by default. The gateway is the single network entry point for all client traffic.

Each service exposes a `HOST` env var (name varies per service) so operators can
override the bind address when needed (e.g. Docker networking, team server
deployments). The default in every `manifest.json` / `manifest.ts` is `127.0.0.1`.

| Service | Env var | Default |
|---------|---------|---------|
| rest-api :5050 | `REST_API_HOST` | `127.0.0.1` |
| workflow :7778 | `WORKFLOW_HOST` | `127.0.0.1` |
| marketplace :5070 | `KB_MARKETPLACE_HOST` | `127.0.0.1` |
| marketplace-registry :5071 | `KB_REGISTRY_HOST` | `127.0.0.1` |
| studio :3000 | `HOST` | `127.0.0.1` |
| state :7777 | — | `127.0.0.1` (hardcoded) |
| gateway :4000 | — | `0.0.0.0` (intentional) |

## Consequences

### Positive

- Fresh `kb-create` installs expose only one port to the local network
- Internal services cannot be reached directly without going through gateway auth
- Matches user mental model: "one URL, everything goes through gateway"

### Negative

- Docker deployments require explicitly setting HOST env vars to `0.0.0.0` or
  the container network address — this must be documented in the Docker guide
- If gateway goes down, internal services are unreachable even locally (same as
  before, but now more obvious)

### Alternatives Considered

- **Firewall rules (pfctl/iptables)** — external to the codebase, fragile across
  OS versions, not portable; rejected
- **Unix domain sockets for inter-service communication** — better long-term
  isolation but requires significant refactoring of service discovery; deferred

## Implementation

- `HOST` env var added to `studio/app/server.js` (`server.listen(PORT, HOST)`)
- `WORKFLOW_HOST`, `REST_API_HOST`, `KB_MARKETPLACE_HOST` env vars already
  respected in respective bootstrap files; defaults changed in manifests
- `KB_REGISTRY_HOST` default changed from `0.0.0.0` to `127.0.0.1` in manifest
- `.kb/devservices.yaml` regenerated by `kb-create` on next install will carry
  loopback defaults automatically via `EntryForSwap` in `from_manifest.go`
